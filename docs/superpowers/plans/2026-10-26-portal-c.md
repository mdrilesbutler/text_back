# Candidate C: the 100-point /client portal — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the /client owner portal that scores 5 on all ten bake-off criteria, as a fenced comparison build on branch `ui/compare-c` (worktree `~/projects/text_back-ui-c`).

**Architecture:** A's render layer (Jinja2 templates under `templates/client/`, one layered `portal.css`, one ES module `portal.js`, self-hosted fonts, strict CSP, CSRF on every POST, JS-off fallbacks) is the shell. A's Messages page is ported and extended. B's backend modules for scheduling, phone/forwarding, home data, calendar and availability are ported as Python modules with their ship blockers fixed; their pages are re-templated to the winning mockup in `docs/notes/portal-c/design/`. New modules: `portal_status.py` (Home truth), `portal_sample.py` (sample conversation from the real handlers), `portal_dates.py` (one date formatter), `portal_registry.py` (live texting-approval status).

**Tech Stack:** Python 3.12, FastAPI, Jinja2, SQLite (`Store`), vanilla JS, Playwright (walk/smoke), pytest.

**Spec:** `docs/notes/ui-bakeoff-2026-10-26/design-prompt-100.md` Part 2, plus `docs/notes/portal-c/research/SUMMARY.md`, `docs/notes/portal-c/copy-deck.md` and the winning mockup in `docs/notes/portal-c/design/`.

## Global Constraints

- Product name on screen: **TextBack**. Banned on every /client screen (test enforced): `SignalWire`, `text_back`, `campaign`, `brand`, `10DLC`, `registration`, `segment`, `lead`, `token`, `webhook`, `provider`, `event ID`, `call_sid`, `nudge`, `hand-off`/`handoff`, and any `{` in visible text.
- Texting number is read-only: "Set up by FluxWorks. It can't be changed here." No swap, edit or port path anywhere.
- Customers never get a live human; `tests/test_no_live_human_copy.py` stays green and gains the template scan from B.
- STOP stays in the opt-out line; `messages.validate_templates` is the only validator (server side).
- No booking claimed without a calendar event ID; business specifics in config / `client_settings`, never code.
- Every date on screen comes from a datetime through `portal_dates.when()`; no hand-written weekdays. Every chip's selected state comes from the field value.
- 390 px: tap targets ≥ 44 px, business name wraps (never ellipsized), sticky chrome ≤ 170 px total. Desktop sidebar is `position: sticky`.
- Toasts render under the sticky header with `role=status`, never over the h1; the save bar appears only with unsaved changes and sets `scroll-padding-bottom`.
- No dev text, hosts or ports in any rendered string; preview links use `state.public_base_url`.
- Fence: no PR from `ui/compare-c`, no merge, no deploy, no API keys, never touch 8000/443/8443/8765/8003, runtime config, credentials, `deploy/textback-designer/`, `docs/demo/`.
- Commits: `git -c user.name="Michael Riley" -c user.email="mdriles@gmail.com" commit --only <paths>`; one commit per layer.

## Review Focus

1. Owner narrows working hours while a booking retry is pending for a slot whose calendar event already exists → the retry must recover the event and confirm, not refuse (Task 5 test `test_recovery_runs_before_the_hours_check`).
2. A direct call to the texting number (no `ForwardedFrom`) → forwarding step stays "Not yet", never "Done" (Task 6 test `test_direct_call_never_ticks_forwarding`).
3. Business name saved with an `&`, an apostrophe or 60 characters → header wraps to two lines at 390 px, first-text preview and rename offer escape correctly (Task 6 test `test_rename_offer_counts_texts_that_still_say_the_old_name`, Task 1 render test).
4. Owner saves Scheduling while a customer is mid-conversation → confirmation copy must match the code: hours and length apply now (checked at booking), quiet hours apply to the next send, already-scheduled reminders keep their time (Task 5 test `test_save_confirmation_matches_live_behaviour`).
5. Registration API unreachable or unconfigured → Home and Messages show "waiting / unknown" wording and the network-notice line stays visible; never "approved" from a stale file (Task 3 test `test_texting_approval_unknown_when_registry_unreachable`).
